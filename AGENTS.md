## BAILEY BOSS — mandatory Superpowers development protocol (owner directive, 2026-11-16)

**OWNER OVERRIDE — ALL SUPERPOWERS SKILLS, NOT JUST THOSE AN AGENT SELECTS AS RELEVANT.** For every BAILEY BOSS / RoofOS engineering work package and its decisions until project acceptance or an explicit owner amendment, retrieve and review **every skill** in the current upstream `https://github.com/obra/superpowers/skills` catalog before deciding or acting. Follow the complete cross-skill workflow and audit every skill; do not silently narrow the catalog to a subjective subset. New upstream skills join the mandatory inventory automatically. For each skill, record concrete application/evidence or a precise dependency/blocker; never claim unexecuted steps, nonexistent subagents, or unavailable tests were performed. Apply the strongest compatible controls in cases of overlap; never violate the approved design, security, owner authority, or the tool's real capabilities.

**Source of truth and precedence:** The owner-approved `ContractorOS_Unified_Master_Dossier.pdf` and its original source requirements govern product scope; reconcile with `ROOFOS-BUILD-CHECKLIST.md`, `UPDATE-CHECKPOINT-LAW.md`, `HANDOFF.md`, `CURRENT-STATE.md`, and the actual GitHub `main` implementation **before edits**. More recent approved specifications supplement rather than silently replace prior requirements. Maintain a requirement-to-code-and-test trace; distinguish proposed, implemented, tested, field-verified, and production-operational states. Do not substitute a new design for a previously approved one.

**Mandatory full-inventory workflow — all 15 upstream skills verified 2026-11-16:** Review each `SKILL.md` at the beginning of every engineering work package, follow its requirements at the right stage, and record the outcome for **every** item below in the work-package ledger or PR. Do not skip an item merely because an agent considers it irrelevant. The status must be `performed`, `blocked` (with exact limitation), or `not triggered` (with the verified triggering condition); `not triggered` is a documented review of the skill, **not** a claim of execution. In particular, parallel subagents cannot be invented and a merge cannot be declared green without completed checks.

1. `using-superpowers` — read the current upstream skill inventory before decisions and confirm the complete set was considered.
2. `brainstorming` — reconcile user intent with the already-approved engineering dossier; capture designs and owner approvals without reopening settled requirements.
3. `writing-plans` — map requirements to executable, file-specific, verifiable tasks and record engineering rulings.
4. `using-git-worktrees` — isolate work; verify SD3 mounting before a Chromebook clone/worktree. A GitHub-only branch is an explicitly disclosed fallback, not a claimed local worktree.
5. `test-driven-development` — test-first RED → GREEN → REFACTOR with actual results for implementation/behavior changes; document why a pure policy change has no executable behavior to test.
6. `systematic-debugging` — trace root causes of problems or failed tests, and log diagnosis; inspect baseline failures before code changes.
7. `executing-plans` — use the plan-driven inline execution ledger and verify each task, including when another worker implements part of the plan.
8. `subagent-driven-development` — review the implementation/reviewer gates for each independent task; use actual subagents only when a supported dispatch tool exists, otherwise record the blocked dispatch and apply independent review controls manually.
9. `dispatching-parallel-agents` — evaluate independence and delegation safety; dispatch only through supported tools, never invent a parallel agent or assert one ran.
10. `requesting-code-review` — request evidence-based review with specific acceptance criteria or record the precise missing reviewer capability.
11. `receiving-code-review` — process actual review feedback, check assertions against code/tests, and document disposition, even if no comments were submitted.
12. `verification-before-completion` — run and inspect appropriate tests/checks and record hard evidence before making any completion, safety, green, or deployment claim.
13. `finishing-a-development-branch` — evaluate PR/merge/cleanup against owner checkpoint law, review state, branch protection, CI status, and independent deployment/field evidence.
14. `writing-skills` — evaluate and test any newly written/updated skill; when only project instructions change, review this skill and explicitly state that upstream reusable SKILL.md content was not edited.
15. `diagnosing-superpowers` — when prior sessions repeat work, ignore a plan, fail to invoke a skill, or otherwise go wrong, investigate against verifiable session transcripts and report evidence and exact limitations; never invent transcript access, analysis, or a diagnosis.

**Ledger template for every work package:** `upstream skill name + revision/URL | reviewed | applied action and evidence | performed/blocked/not triggered | blocker or next action`. Keep the 15 entries in `HANDOFF.md`, a task-specific engineering log, or PR body. Do not use `not triggered` merely to avoid an inconvenient skill. If future upstream changes the inventory, enumerate the new list before the next task. This is mandatory even when a task appears small.

**Sequence and conflicting execution models:** Cover all skill checkpoints without running inherently incompatible modes at once. `executing-plans` provides the inline executor; `subagent-driven-development` and `dispatching-parallel-agents` are additionally audited, and used when actual isolated agent dispatch is supported and appropriate. Preserve security, privacy, free-only, backup, checklist, and green-merge rules regardless of any skill example. A skill audit is not proof that a skill's external action occurred.

**Platform reality:** Installing Superpowers in OpenCode, Codex, or another coding runtime is a separate action per runtime, using that runtime's upstream instructions. If a host cannot invoke a skill natively, read its upstream `SKILL.md` and apply the method manually, identifying the limitation. Do not invent subagent execution or local tests.

**Authority and cost:** Open-source/free-first only; never incur paid API/model charges or alter billing without explicit approval. No unapproved external submissions, material orders, production database changes, or restricted actions. This protocol cannot bypass direct owner instructions, security requirements, or applicable law.
