# ROOF/OS AI Receptionist Runbook

## Current status — 2026-10-20

The receptionist code path remains an optional add-on, not part of the Free Core release claim. Twilio voice/SMS and Stripe Checkout require paid third-party accounts and are disabled unless the owner explicitly enables them. The default AI direction is local Ollama; no OpenAI/Gemini or other hosted-AI key is required or permitted for the Free Core path.

The runbook describes provider boundaries and safety rules. It does not prove that a live Twilio number, Stripe account, receptionist worker, or authenticated end-to-end call has been configured.

## Current production path

The lowest-cost shippable release uses **Twilio pay-as-you-go voice/SMS transport**, **Stripe-hosted Checkout payment links**, Supabase for durable state, and a server-side constrained dialogue model. Twilio and Stripe are isolated behind webhook and adapter routes, so transport can later move to a SIP carrier or self-hosted Asterisk/LiveKit/Pipecat without changing lead, calendar, consent, or payment policy.

The release supports inbound calls, outbound calls initiated by an authenticated workspace user, SMS follow-up initiated by an authenticated workspace user, opt-out handling, human transfer, existing-calendar appointment creation, issued-invoice payment links, signed Stripe webhooks, durable sessions, and append-only provider events.

## Required server secrets

Set the following in the server-side deployment environment, never in browser or mobile variables:

- `SUPABASE_SERVICE_ROLE_KEY`
- `STRIPE_SECRET_KEY`
- `STRIPE_WEBHOOK_SECRET`
- `TWILIO_ACCOUNT_SID`
- `TWILIO_AUTH_TOKEN`
- `TWILIO_PHONE_NUMBER`
- `OLLAMA_BASE_URL` (server-side URL for the owner-managed local Ollama service, only when receptionist AI is enabled)
- `RECEPTIONIST_AI_MODEL` (owner-selected local Ollama model; do not set this to a hosted paid model)
- `RECEPTIONIST_WORKSPACE_ID`
- `RECEPTIONIST_OWNER_ID`
- `RECEPTIONIST_PUBLIC_URL`
- `RECEPTIONIST_TRANSFER_NUMBER`

The workspace and owner identifiers are server configuration, not caller-provided values. The initial release maps one configured Twilio number to one workspace. Multi-workspace number routing should be implemented before exposing multiple workspaces through the same number.

## Provider webhooks

Configure Twilio voice webhooks as follows:

- Voice incoming: `POST /api/receptionist/twilio/voice`
- Conversation turn: generated by the voice route as `POST /api/receptionist/twilio/turn`
- Call status: `POST /api/receptionist/twilio/status`
- SMS incoming: `POST /api/receptionist/twilio/sms`
- Outbound TwiML: generated by the outbound route as `POST /api/receptionist/twilio/outbound/twiml`

Configure Stripe webhook delivery to `POST /api/receptionist/stripe/webhook` and subscribe to Checkout completion, expiry, payment failure, and refund events. The webhook secret must be the endpoint-specific signing secret. The server verifies the raw body before updating payment state.

## Operator controls

Before enabling outbound traffic, set a local quiet-hours policy, verify the company transfer number, review call-recording and transcript retention, and document the consent basis for each calling jurisdiction. The AI may not quote prices, modify balances, approve estimates or supplements, promise start dates, or collect payment credentials. A human must approve an invoice by marking it `issued` before a payment link can be generated.

## Three-level release check

Level 1 runs `npm run test:receptionist`, `npx tsc --noEmit`, `npm run verify:security`, `npm run build`, and `git diff --check`. Level 2 uses a staging Twilio number and Stripe test mode to exercise inbound voice, outbound voice, SMS, opt-out, transfer, conflict-safe appointment booking, issued-invoice payment links, and duplicate webhook delivery. Level 3 uses two workspaces and confirms RLS isolation, caller/session correlation, webhook idempotency, secret absence from bundles and logs, quiet-hour enforcement, and human escalation.

## Open-source evolution

When call volume or data-control requirements justify self-hosting, keep ROOF/OS’s domain adapters and move only the media transport. The strongest open-source candidates are Asterisk + Pipecat for maximum control, or LiveKit Agents + LiveKit SIP for a more integrated WebRTC/SIP foundation. Both still require a carrier/SIP trunk, real-time networking, model providers or local inference, observability, recording controls, fraud protection, and an on-call operator. This is a later cost/control optimization, not the lowest-cost initial deployment.
